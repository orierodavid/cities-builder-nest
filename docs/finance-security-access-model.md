# Finance security and provider-neutral access model

Status: design constraints only. No payment provider has been selected. This document does not activate payment processing or grant client access to financial records.

## Current boundary

- The API currently has no payment-intent, withdrawal, ledger, provider-webhook, or reconciliation routes.
- RLS is enabled on finance tables. Client roles have no table privileges on payment intents, withdrawals, ledger transactions/entries, provider events, reconciliation runs/exceptions, or audit logs.
- Authenticated users can read active rows from `financial_partners` through the existing RLS policy.
- Residents can select, insert, and update their own `rent_savings_goals` under existing ownership policies. Deletes are not granted.
- Trusted server operations use the Supabase service role. Never expose its key to mobile/web clients.

## Authorization rules for future endpoints

### Savings goals
- Derive resident identity from the verified Supabase access token; never accept `resident_user_id` as an authority from request JSON.
- Verify active estate membership when a goal is tied to an estate.
- Validate target amount as positive integer NGN kobo and validate status transitions server-side.
- A resident may read/update only their own goal. No client deletion unless a separately reviewed product requirement justifies it.

### Payment intents (provider-neutral)
- Create intents only on the server after checking goal ownership and amount/currency.
- Generate unique idempotency keys and internal references server-side.
- Treat client redirects/screens as informational only; mark a payment successful only after authenticated server-to-server verification with the eventual provider.
- Store provider-specific data only behind an adapter boundary after a provider is chosen. Do not invent provider fields or webhook verification now.

### Withdrawals
- No direct client write to withdrawal tables.
- Before any future withdrawal workflow, define approval policy, destination verification, balance reservation, idempotency, step-up authentication and failure/reversal behavior.
- Never accept a client-supplied balance or mark a withdrawal paid from a client request.

### Ledger
- Append-only accounting records; no client insert/update/delete.
- Ledger entries must be generated by trusted server-side business operations and be consistent with the parent transaction and resident.
- Corrections should use reversal/adjustment entries, not mutation of historical entries.

### Provider events and reconciliation
- Accept events only through a provider-specific verified webhook endpoint once a provider is selected.
- Verify signatures against the raw request body, enforce replay protection/idempotency, and record event processing outcomes.
- Reconciliation jobs are service-only; expose aggregate/status views only after explicit authorization design.

### Audit logs
- Writes only from trusted server-side code or database triggers.
- No client read/write access by default. Define a narrowly scoped finance-admin audit viewer separately if needed.

## Required before choosing/enabling a provider

1. Select provider and confirm supported NGN collection/payout methods, settlement model, fees, webhook signing, and refund/reversal support.
2. Define who legally holds funds and who is responsible for custody, KYC/AML, refunds, disputes, and reconciliation.
3. Review the financial-partner custody model with legal/compliance and the provider; do not imply that the app itself holds deposits unless that is actually approved.
4. Implement provider adapter, verified webhook, idempotency and reconciliation tests.
5. Add least-privilege server-side authorization and test cross-resident/cross-estate access.
6. Keep finance tables client-inaccessible unless a specific, reviewed user-facing read path requires a narrowly scoped policy.

## Security posture

RLS-without-policies is intentional for the server-only finance tables at this stage. The Supabase security advisor may continue to report these as informational findings; do not silence them by adding broad policies. Review leaked-password protection separately in Supabase Auth settings.
